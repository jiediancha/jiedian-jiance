# 节点检测方法 2026 · 延迟、超时与可用性怎么测（持续更新）

**延迟低不等于能用。** 客户端里那个绿色的 `86ms` 只说明「测试请求成功回来了」，它既不保证你能打开网页，也不保证晚上还是这个数。真正决定体验的是三件互相独立的事，必须分开测：

1. **连通性** —— 这条节点现在能不能建立连接。失败就是失败，没有中间态。
2. **延迟** —— 建立连接后一来一回要多久。影响的是「点开的瞬间卡不卡」。
3. **带宽** —— 单位时间能搬多少数据。影响的是「视频糊不糊、下载快不快」。

一条延迟 60ms 的节点可能带宽只有 2Mbps，看 1080p 就转圈；一条延迟 300ms 的节点可能跑满 100Mbps，下载飞快但打游戏难受。**三个指标不能互相推断**，这是本页所有方法的出发点。

本页只讲**一条节点怎么自己测**：用什么工具、看哪个数、多少算正常、结果怎么读。不讲服务商好坏，不做推荐，不含任何推广链接。

> **数据核对日期：2026-08-14**
> 本页的阈值区间是网络工程里通用的经验参考范围，不是本页作者的实测结果。任何具体到某条线路、某个时段的数字，都必须你自己在自己的网络上测出来 —— 别人的数在你这里不成立。

## 一、四个指标各自怎么测

| 指标 | 怎么测 | 参考区间（通用经验值，非实测） | 主要受什么影响 | 常见误读 |
| --- | --- | --- | --- | --- |
| **延迟 RTT（ms）** | `ping <地址>`；HTTP 层用 `curl -o /dev/null -s -w "%{time_total}\n" <URL>` | 同城/直连 10–40；跨境优化线路 60–150；跨境普通线路 150–300；>300 明显影响交互 | 物理距离、绕路、链路拥塞、排队 | 把一次 ping 当结论。延迟必须看**连续多次的分布**，不是单次值 |
| **丢包率（%）** | `ping -n 100 <地址>`（Windows）/ `ping -c 100 <地址>`（macOS、Linux），看统计行的 loss | 0% 正常；0.1–1% 一般无感；1–3% 网页开始偶发卡顿；>5% 通话与游戏基本不可用 | 链路拥塞、中间设备主动丢弃、本地 Wi-Fi 干扰、限速触顶 | 把丢包算进延迟里。**丢的那些包不产生延迟数字**，所以链路越烂，平均延迟看起来可能反而越好看 |
| **抖动 Jitter（ms）** | 同一批 ping 结果里，最大值减最小值；或看多次结果的标准差 | <20 稳定；20–50 通话偶有杂音；>50 语音视频明显断续 | 链路排队波动、共享带宽争抢、无线信号 | 只盯平均延迟。**平均 80ms 但在 40–400 之间跳**的线路，体验远差于稳定的 150ms |
| **下载带宽（Mbps）** | 浏览器跑一次测速站；或 `curl -o /dev/null -w "%{speed_download}\n" <大文件URL>`（结果单位是字节/秒，×8÷1000000 得 Mbps） | 看 1080p 需稳定 ≥5；4K 需 ≥25；这两个门槛是**持续**值不是峰值 | 服务商限速、并发人数、时段、本地宽带上限 | 拿峰值当结论。带宽要看**持续 10 秒以上的平均**，前 2 秒的冲高不算数 |

### 测量前必须先排除本地因素

这一步跳过的话，后面测出来的所有数都不可信：

- **先测不走代理的直连延迟**（ping 你的宽带网关、或国内某个大站）。本地就丢包，节点再好也没用。
- **优先用网线**，或至少确认 Wi-Fi 信号强度正常。无线抖动能凭空制造 30ms 以上波动。
- **关掉正在下载/上传的程序**，包括后台的云盘同步和系统更新。带宽被占满时延迟会整体抬高。
- **确认没有第二层代理**。系统代理 + 客户端代理叠在一起，测的是两跳的和。

## 二、Clash 里的延迟到底是什么

打开 Clash 系客户端（Clash Verge、Clash Meta / mihomo、以及各类基于它们的分支）点「测延迟」，那个数字的产生方式是：**客户端通过这条节点，向一个固定的测试 URL 发一次 HTTP(S) 请求，记录从发起到收到响应头的耗时。**

理解这句话，就能解释一堆看起来矛盾的现象：

| 现象 | 原因 |
| --- | --- |
| 显示 80ms，但网页打开很慢 | 测的是**一次**请求的握手往返，不含后续传输。带宽小、或长连接被中途限速，都不会反映在这个数字上 |
| 显示 80ms，但看视频一直缓冲 | 同上。延迟测试完全不测带宽 |
| 同一条节点，两次测差 200ms | 单次采样。要判断稳定性得连续测多次看波动，而不是刷新到一个好看的数为止 |
| 所有节点延迟都变高了 | 大概率是本地网络或测试 URL 侧的问题，不是每条节点同时变坏 |
| 换了个客户端，同一节点数字对不上 | **不同客户端默认的测试 URL 不同**，测试目标不同，数字自然不同。跨客户端比较延迟没有意义 |
| 延迟正常但提示超时 | 测试 URL 被目标侧限制或需要额外校验，请求发得出去但拿不到预期响应 |

### 三条使用建议

1. **只用它做相对比较**，判断「同一时刻、同一客户端下，哪条节点更快」。别把它当绝对性能指标。
2. **改测试 URL 会改变结论。** 想测「看视频顺不顺」，就该把测试目标换成你实际要访问的服务的域名 —— 测一个和你用途无关的地址，结果和你的体验没有必然关系。
3. **延迟测试通过 ≠ 该服务可用。** 能拿到响应头，不代表这条线路对目标服务是通的。可用性要用实际访问来验证，不能用延迟数字替代。

## 三、故障对照表：看到这个现象，先查这个

按现象定位，从上往下逐条排除。**先查排查顺序里靠前的那一条，别一上来就换节点。**

### 现象 A：节点列表全红 / 全部超时

| 排查顺序 | 检查什么 | 怎么确认 |
| --- | --- | --- |
| 1 | 本地网络是否正常 | 关掉代理，能不能正常上网。不能 → 问题在本地，与节点无关 |
| 2 | 系统时间是否准确 | 时间偏差过大会导致 TLS 握手失败，表现为全部节点连不上。校时后重测 |
| 3 | 订阅是否已过期或流量耗尽 | 到服务商后台看剩余流量与到期日。**这是全红最常见的原因之一** |
| 4 | 订阅链接是否失效 | 手动更新订阅，看是否报错。有些订阅地址会因服务商域名变更而整体失效 |
| 5 | 客户端配置是否损坏 | 换一个客户端导入同一份订阅。换了就好 → 问题在原客户端配置 |

> 关键判据：**全红几乎不可能是「所有服务器同时挂掉」。** 一个共同的上游因素坏了才会全红，而那个因素通常在你这一侧或账号这一侧。

### 现象 B：部分节点红、部分正常

| 排查顺序 | 检查什么 | 怎么确认 |
| --- | --- | --- |
| 1 | 红的是不是集中在同一地区/同一组 | 是 → 该落地或该中转线路的问题，换其它地区先用着 |
| 2 | 红的是不是都是「高倍率 / 专线」组 | 有些线路对流量倍率或套餐等级有限制，不在你的套餐内就连不上 |
| 3 | 是否只在某个时段红 | 是 → 拥塞导致的超时，不是节点故障。见下方三日流程 |
| 4 | 换个测试 URL 是否还红 | 换了就正常 → 是测试目标的问题，不是节点的问题 |

> **部分红是正常状态，不是故障。** 任何一份订阅里都会有一部分节点在某些时刻不可用。只要你常用的那几条稳定，不必追求全绿。

### 现象 C：能连上但打不开网页

这类问题的共同点是：**传输层通了，应用层没通。**

| 可能原因 | 判别方法 |
| --- | --- |
| 分流规则把该域名走了直连 | 看客户端的连接日志，确认这条请求实际走的是哪条规则 |
| DNS 解析出了问题 / DNS 泄漏 | 换用节点侧解析（remote-dns / fake-ip）后重试；解析到了错误的地址就打不开 |
| 目标站点本身对该出口 IP 有限制 | 换一条不同落地的节点试同一个网址。换了就好 → 是出口 IP 被限，不是节点坏 |
| 浏览器缓存了失败状态 | 无痕窗口重试，或清一次该站点的缓存 |
| 客户端代理模式没生效 | 访问一个能显示出口地址的页面，确认当前出口确实变了 |

### 现象 D：忽快忽慢

| 可能原因 | 判别方法 |
| --- | --- |
| 时段性拥塞 | 同一条节点，白天和晚高峰各测一次带宽。差距大 → 拥塞 |
| 服务商限速策略 | 前几十秒快、之后掉下来并稳定在某个值 → 典型的限速触发曲线 |
| 本地 Wi-Fi 不稳 | 换网线复测。抖动明显收敛 → 问题在无线 |
| 客户端自动切换节点 | 关掉自动选择，锁定单条节点复测。锁定后就稳 → 之前是在不同节点间跳 |
| 家庭宽带上行被占满 | 上传占满会拖垮下载体验。先停掉后台上传再测 |

## 四、可复现的三日自测流程

单次测量在这个场景里几乎没有判断价值 —— 因为**同一条节点在不同时段的表现差异，常常大于不同节点之间的差异**。所以要测就测出可比的数据。

### 为什么是「连续三天、同一时段」

- **同一时段**：控制住最大的变量。晚高峰和凌晨的同一条线路可以是两个东西，跨时段的数字不能互相比较。
- **连续三天**：区分「偶发」和「稳定劣化」。一天不好可能是当晚的临时拥塞或线路抖动，三天都不好才是这条节点的真实水平。
- **同一台设备、同一网络**：换设备或换 Wi-Fi 就等于换了被测系统，前后数据作废。

### 每次测量做四步

**第 0 步（每次都做）**：关代理，测直连基线 —— `ping` 国内任一大站 100 次，记下平均延迟和丢包。基线异常就今天不测了，先修本地网络。

**第 1 步 · 连通性**：客户端里对候选节点各测一次延迟，记下「通 / 不通」。不通的直接出局，不必再测后面三项。

**第 2 步 · 延迟与抖动**：对每条候选节点，连续 ping 目标地址 100 次，记录：
- 平均延迟
- 最小值与最大值（两者之差就是抖动的粗略度量）
- 丢包率

**第 3 步 · 带宽**：跑一次持续 10 秒以上的下载测速，记录**稳定段的平均值**，不是峰值。

**第 4 步 · 实际可用性**：打开你日常真正要用的那几个站点/服务，各花 30 秒实际用一下。这一步无法被任何数字替代 —— **前三步全绿而第四步不行，以第四步为准。**

### 三天结束后怎么读数据

| 三天的表现 | 结论 |
| --- | --- |
| 三天都稳定，波动 < 20% | 这条节点在这个时段可用，可以固定下来 |
| 两天好一天差 | 偶发。留作备用，继续观察，别急着换 |
| 三天逐日变差 | 稳定劣化。可能是该线路人数增长或策略变化，考虑换线路 |
| 每天同一时段差、其它时段好 | 时段性拥塞。不是坏，是那个时段该线路负载高 |
| 数字都好但第 4 步一直不行 | 不是性能问题，去看现象 C 的排查表 |

## 六、FAQ

**Q：延迟多少算好？**
没有绝对标准，要看用途。文字浏览 300ms 以内基本无感；视频通话希望 150ms 以内且抖动小；实时对战类通常越低越好。**比绝对值更重要的是稳定性** —— 稳定的 150ms 通常比在 40–400 之间跳动的「平均 90ms」体验好得多。

**Q：为什么白天快、晚上慢？**
共享带宽的争抢。晚间是用网高峰，同一条链路上的人变多，排队变长 → 延迟升高、抖动变大、带宽被摊薄。这是共享资源的正常表现，不一定说明线路坏了。判别方法：**同一条节点凌晨再测一次**，如果凌晨正常，就是时段性拥塞而不是故障。

**Q：测速软件的结果准吗？**
它准确反映的是「刚才那次、到那个测速服务器、在那个时刻」的速度，仅此而已。跨测速站、跨时段、跨设备的结果不能互相比较。要让结果有意义，就固定测速站、固定时段、固定设备，只比较自己前后的数据。

**Q：ping 通了为什么还是打不开网页？**
ping 走的是 ICMP，网页走的是 TCP + TLS + HTTP。前者通只说明网络层可达。中间任何一层出问题（DNS 解析错误、TLS 握手失败、目标对出口 IP 有限制、分流规则走错）都会导致「ping 通但打不开」。见现象 C 的排查表。

**Q：为什么客户端显示的延迟和 ping 的结果差很多？**
测的不是同一件事。ping 测的是到某个 IP 的 ICMP 往返；客户端测的是通过节点完成一次 HTTP(S) 请求的耗时，包含 TCP 握手、TLS 协商和服务端响应时间。后者天然更大，而且受测试 URL 影响。**两个数字不具备可比性。**

**Q：丢包 1% 严重吗？**
取决于用途。网页浏览基本无感（TCP 会重传）；视频通话和实时对战会明显感觉到，因为它们对时延敏感、重传来不及。但要注意：**1% 的丢包如果集中爆发（连续丢十几个）**，比均匀分布的 1% 难受得多，所以还要看 ping 输出里丢包是分散的还是成串的。

**Q：换个节点就好了，是不是原来那条坏了？**
不一定。有可能是目标站点对原来那个出口 IP 有限制，也可能是你换节点的同时触发了重新连接。**要确认是节点问题，得回头再连原来那条复测一次** —— 如果又正常了，那说明是偶发，不是这条节点的固有问题。

**Q：需要每天都测吗？**
不需要。日常用着顺畅就不用测。测量是**出问题时的诊断手段**，或者**换线路前的评估手段**。日常盯着延迟数字刷新，只会让你在正常的波动里找出并不存在的问题。

**Q：多条节点同时开着测，结果会互相影响吗？**
会。多条同时跑测速会争抢你本地的带宽，测出来的每一条都偏低。**测带宽必须一条一条来。** 延迟测试影响较小，但严格起见也应串行。

**Q：手机和电脑测出来不一样，信谁的？**
信你实际用的那台。两者的网络栈、无线信号、后台流量都不同，本来就不该一样。**要比较节点优劣，就固定在同一台设备上比。**
